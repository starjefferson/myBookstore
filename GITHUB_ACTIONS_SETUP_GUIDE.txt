1. WHAT THIS AUTOMATION DOES & SYSTEM ARCHITECTURE
================================================================================
This project uses a decoupled two-step ingestion and seeding pipeline:

  node scripts/scrape.js

Queries WooCommerce REST APIs across all three vendors (Masobe, Rovingheights, 
and Retala) in batches of 24 items per page. It saves local catalog snapshots to:

  scraped_catalog.json
  lib/categoryFilters.json

  node scripts/seed.js

Reads scraped_catalog.json and performs quota-safe batch upserts to Firebase 
Firestore. Upon successful database writes, it fires a POST webhook call to 
/api/revalidate to automatically purge the Next.js API cache.

GitHub Actions runs these commands automatically on a cloud runner twice a week:

  1. Download the repository code.
  2. Install Node.js 22 and project dependencies (npm ci).
  3. Execute scrape.js (routes Rovingheights via ScraperAPI to bypass WAF).
  4. If scraping succeeds, execute seed.js (batch upserts catalog & shipping zones).
  5. Fire the Next.js revalidation webhook to instantly update live API caches.
  6. Upload scraped JSON files as workflow artifacts.

The workflow is located at:
  .github/workflows/scrape-catalog.yml

================================================================================
2. LOCAL DEVELOPMENT WORKFLOW
================================================================================
You can continue running the commands locally on your development machine:

  node --env-file=.env.local scripts/scrape.js

After checking the generated scraped_catalog.json, upload it manually with:

  node --env-file=.env.local scripts/seed.js

The npm equivalents are:
  npm run scrape
  npm run seed

However, because standard npm scripts may not automatically load .env.local on 
older Node setups, use the explicit node --env-file=.env.local commands above unless 
your environment variables are loaded another way.

Recommended local workflow:
  1. Run scrape.js.
  2. Wait for "Catalog ingestion complete".
  3. Inspect scraped_catalog.json for book count, vendor, and author values.
  4. Run seed.js only when you are ready to update Firestore and invalidate cache.

The scraper does not write to Firestore. The seeder is the only script that writes 
the catalog to Firestore.

3. BEFORE SETTING UP GITHUB ACTIONS
================================================================================
You need:
  - A GitHub account.
  - This project pushed to a GitHub repository.
  - The repository must contain package.json and package-lock.json.
  - A Firebase project with Firestore enabled.
  - Firebase Admin credentials for server-side Firestore access.
  - A ScraperAPI key (for Rovingheights proxying).
  - A custom REVALIDATION_SECRET_TOKEN generated by you.

Never commit .env.local, Firebase private keys, or service-account JSON files to 
GitHub. Anyone who obtains the private key may gain full access to your database.

PART 2: CONFIGURE REPOSITORY SECRETS
================================================================================
The workflow requires six repository secrets under GitHub Repo -> Settings -> 
Secrets and variables -> Actions -> New repository secret:

  1. FIREBASE_PROJECT_ID: Your Firebase project ID string.
  2. FIREBASE_CLIENT_EMAIL: Service account client email.
  3. FIREBASE_PRIVATE_KEY: Full RSA key including -----BEGIN PRIVATE KEY----- and -----END PRIVATE KEY-----.
  4. SCRAPER_API_KEY: Your ScraperAPI account key (for Cloudflare bypass).
  5. REVALIDATION_SECRET_TOKEN: Your custom secret passkey (e.g. my_secret_token_2026).
  6. NEXT_PUBLIC_APP_URL: Your production domain (e.g. https://your-domain.vercel.app).

Do not paste variable names into value fields. GitHub masks secrets in logs, 
so avoid printing them in your code.

PART 3: CHECK THE WORKFLOW FILE
================================================================================
Location: `.github/workflows/scrape-catalog.yml`

name: Catalog Scrape and Seed

on:
  schedule:
    # Runs twice a week: Mondays & Thursdays at 02:00 UTC (03:00 WAT)
    - cron: "0 2 * * 1,4"
  workflow_dispatch:

jobs:
  catalog-sync:
    runs-on: ubuntu-latest
    timeout-minutes: 15

    env:
      FIREBASE_PROJECT_ID: ${{ secrets.FIREBASE_PROJECT_ID }}
      FIREBASE_CLIENT_EMAIL: ${{ secrets.FIREBASE_CLIENT_EMAIL }}
      FIREBASE_PRIVATE_KEY: ${{ secrets.FIREBASE_PRIVATE_KEY }}
      SCRAPER_API_KEY: ${{ secrets.SCRAPER_API_KEY }}
      REVALIDATION_SECRET_TOKEN: ${{ secrets.REVALIDATION_SECRET_TOKEN }}
      NEXT_PUBLIC_APP_URL: ${{ secrets.NEXT_PUBLIC_APP_URL }}

    steps:
      - name: Check out repository
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run REST Catalog Ingestion Engine
        run: node scripts/scrape.js

      - name: Seed Firestore
        run: node scripts/seed.js

      - name: Upload catalog snapshot
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: scraped-catalog-${{ github.run_id }}
          path: |
            scraped_catalog.json
            lib/categoryFilters.json
          if-no-files-found: ignore
          retention-days: 14

================================================================================
ERROR HANDLING & RETRY / SKIP LOGIC
================================================================================
1. Transient Proxy Delays:
   scrape.js uses a 45-second timeout for ScraperAPI proxy calls and 25-second 
   for direct calls, with exponential retry backoff (4s, 8s, 12s) across 3 attempts.

2. Failed Page Skipping:
   If a page fails all 3 attempts, scrape.js logs a warning, skips that page, 
   and continues to page + 1. It only stops when WooCommerce returns an empty array [].

3. Inter-page Throttling:
   Enforces a 1.5-second pause between proxy requests to prevent hitting ScraperAPI 
   rate limits or concurrency locks.

================================================================================
FIRESTORE SAFETY & QUOTA OPTIMIZATION
================================================================================
1. Zero Read Operations: seed.js does NOT call db.collection("books").get(). 
   Saves thousands of read ops per sync, preventing free-tier quota depletion.

2. Chunked Batch Writes: Writes are split into chunks of 450 items per batch 
   (below Firestore's 500 operation limit per batch request).

3. Stable Document IDs: Predictable IDs (`vendor-page-slug`) ensure repeat seeds 
   update existing documents via `{ merge: true }` without creating duplicates.

================================================================================
AUTOMATED NEXT.JS CACHE REVALIDATION ENGINE
================================================================================
To make Firestore updates reflect immediately on the frontend without waiting 
for time-based TTL expiration:

1. Webhook Endpoint (`app/api/revalidate/route.js`):
   Secured with REVALIDATION_SECRET_TOKEN. Calls `revalidatePath('/api/catalog')` 
   and `revalidatePath('/')` to instantly flush CDN edge and route memory caches.

2. Automatic Execution:
   At the end of `seed.js`, `triggerApiRevalidation()` sends an HTTP POST request 
   to `${NEXT_PUBLIC_APP_URL}/api/revalidate?secret=${REVALIDATION_SECRET_TOKEN}`.

3. Result:
   The moment seeding finishes, cache is cleared. Next browser refresh loads 
   the fresh Firestore dataset instantly.
